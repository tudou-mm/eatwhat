# 「吃什么」后端接口契约 v1.5

> 配套实现：`server/`（Spring Boot 3.2 + JPA）
> 所有接口统一返回 `{ code, msg, data }`，`code === 0` 表示成功。
>
> **v1.1 变更**：平台端从「读假数据、写不落库」改造为全量接后端。
> 新增 `/admin/bootstrap`（聚合）、`/admin/audit/*`（商家审核）、
> `/admin/config/publish-rule`（全局发布规则）；`/admin/overview` 补
> `shopPending` / `dishToday` / `trend`；`shopView` 补审核痕迹字段。
>
> **v1.3 变更**：上线前加固三项落地。
> ① **JWT 鉴权**：登录统一到 `POST /api/auth/login`，之后所有管理类请求带
> `Authorization: Bearer <token>`；`/api/admin/**` 要 admin、`/api/merchant/**`
> 要 merchant、`/api/upload` 要 admin 或 merchant。
> ② **CORS 白名单**：不再 `*`，从 `eatwhat.cors.allowedOrigins` 读。
> ③ **文件上传**：新增 `POST /api/upload`，服务端 UUID 重命名 + 魔数校验，
> 静态托管在 `/uploads/**`。
> 另外：**错误响应的 HTTP 状态码与业务 code 一致**（401/403 不再是「HTTP 200 里塞 code」）。
>
> **v1.4 变更**：把「登录之前那道门」补上。
> ① **短信验证码真校验**：新增 `POST /api/auth/sms-code` 发码；
> 客户端登录、商家端登录都真正校验验证码（之前客户端任意 6 位都放行）。
> ② **登录防撞库**：同账号连续失败 5 次锁 15 分钟（锁定期间密码正确也拒），
> 同 IP 每分钟登录尝试上限；发码接口另有「同号 60 秒 + 同 IP 每小时」两道限流。
> ③ **JWT 密钥外置**：走环境变量 `EATWHAT_JWT_SECRET`，
> prod profile 下若仍是开发默认值，服务直接拒绝启动。
>
> **v1.5 变更**：让「封店 / 封号 / 登出」**当场生效**，不留 168 小时的尾巴。
> ① **会话版本号（`tv`）**：签发的 token 里带一个整数，每次请求与库里的当前值比对，
> 对不上就 401。封店、封号、登出时把库里的值 +1 —— 已经发出去的凭证下一毫秒就作废。
> ② **状态闸门**：拦截器每请求查一次主体状态，`banned` 的店 / 用户**所有接口**一律 401
> （原先只有「发布」拦了，改资料、上下架、回评全都照常放行）。
> ③ **新增 `POST /api/auth/logout`**：真正的服务端登出，作废该主体全部已签发凭证。
> ④ **客户端发评论要身份**：`POST /api/client/dish/{id}/comment` 不再从请求体取 `userId`，
> 一律以 token 里的主体为准（原先填谁的 id 就能以谁的名义评论）。
> ⑤ **禁言补上回评拦截**：`ShopService.mute()` 的注释早就写了「不能发布、不能回评」，
> 但回评那条一直没实现，这次补上了。

## 通用约定

| 项 | 说明 |
|---|---|
| Base URL | `http://localhost:8080/api` |
| 请求体 | `application/json` |
| 成功 | `{"code":0,"msg":"ok","data":...}` |
| 业务失败 | `{"code":400,"msg":"距上次发布不足 24 小时…","data":null}` |
| 未找到 | `{"code":404,...}` |
| 服务异常 | `{"code":500,...}` |
| 鉴权 | **JWT（HS256）**，见下节。`Authorization: Bearer <token>` |
| 跨域 | 白名单，配在 `eatwhat.cors.allowedOrigins`（逗号分隔） |

### 鉴权规则

| 路径 | 要求 | 不带 token | 身份不符 |
|---|---|---|---|
| `/api/admin/**` | admin | 401 | 403 |
| `/api/merchant/**` | merchant | 401 | 403 |
| `/api/upload` | admin 或 merchant | 401 | 403 |
| `/api/client/dish/{id}/comment` | **client** | 401 | 403 |
| 其余 `/api/client/**`、`/api/health`、`/api/login` | 公开 | — | — |
| `/api/merchant/apply` | **公开** | — | — |
| `/api/auth/login`、`/api/auth/sms-code`、`/api/auth/logout` | 公开，但**有频率限制** | — | — |

> `/api/merchant/apply` 必须公开：还没有账号的人才能提交入驻申请。
> `/api/auth/logout` 也必须公开：登出恰恰是「凭证可能已经不作数」时最需要能调通的接口，
> 要求先通过鉴权才能登出会把人卡在登录态里出不来。
>
> **HTTP 状态码 = 业务 code**。401 就是 401，不是「HTTP 200 但 code=401」——
> 适配层要靠状态码判断该不该踢回登录页。
>
> ⚠️ **401 与 403 的分工**：401 = 「你这份凭证不作数了」（会被清会话送回登录页）；
> 403 = 「身份是真的、凭证也有效，只是不该走这个门」（会话保持不动）。
> 两者的选择会直接改变前端行为，改之前先想清楚。
>
> **双层越权防护**：URL 层由 `AuthInterceptor` 挡（商家 token 只能碰自己的 shopId）；
> 业务层再加一道，Controller 里 `shopId` 一律以 token 里的为准**强制覆盖** body 里的值，
> 所以「body 里塞别家 shopId」也越不过去。

### 会话作废与状态闸门（v1.5）

JWT 的天生短板是**签发之后服务端就管不了了** —— 校验只认签名和过期时间。
于是会出现这种事：平台端把一家店封了，那家店拿着封店前领的 token 照样能改资料、
上下架菜品、回评，一直用到 168 小时后自然过期。封了等于没封。

补法是给每个可登录主体挂一个**会话版本号**，签发时写进 payload 的 `tv` 字段，
每次请求与库里的当前值比对。**作废 = 把库里的值 +1**。

| 主体 | 版本号存在哪 | 什么时候 +1 |
|---|---|---|
| 商家 | `shop.token_version` | 封店、主动登出 |
| 食客 | `app_user.token_version` | 封号（→ banned）、主动登出 |
| 平台 | `platform_config.admin_token_version` | 主动登出 |

> 平台账号是配置里的固定账号（`eatwhat.auth.adminAccount`），没有实体行，
> 所以版本号寄存在那张单行配置表上 —— 比单为它建一张表划算。

拦截器里一共三道闸，**顺序不能换**：

1. **角色 ↔ 路径匹配**（403）—— 商家 token 打平台端接口直接拒
2. **商家只能碰自己那家店**（403）—— URL 层拦一道，Controller 再兜一道
3. **会话是否仍然有效**（401，`SessionGuard`）—— 这一道要查库，所以放最后，前面能挡的先挡掉

第 3 道内部有两件事，**不能合并成一件**：
- **状态**：`banned` 的店 / 用户一律拒
- **版本号**：`tv` 对不上就拒

`muted`（禁言）**只拦发布和回评，不拦登录** —— 禁言是限制行为，不是变相封店。
店家仍然要能登进来看数据、处理评论。

**登出接口**

```
POST /api/auth/logout        # 公开，带不带 token 都返回 200
Authorization: Bearer <token>   （可选）
→ { "code":0, "data":{ "ok":true, "revoked":true, "role":"merchant" } }
```

幂等：重复调用、不带 token、带一个坏 token，都返回成功 ——
目标是「让这份凭证失效」，它本来就失效的话目标同样达成。

⚠️ 作废的是**该主体的全部会话**，不只是当前这一个。当前设计是「一店一号 / 一人一号」，
所以合理；将来要支持同账号多设备，这里得改成按设备粒度作废。

⚠️ 代价：每个受保护请求多一次主键查询。试点规模可以接受；
要扛量的话应该在这一层加缓存，或改成「吊销名单 + 短 TTL」。

### 登录防撞库与短信验证码（v1.4）

| 规则 | 默认阈值 | 配置项 |
|---|---|---|
| 同账号连续失败 → 锁定 | 5 次 → 锁 15 分钟 | `maxLoginAttempts` / `lockMinutes` |
| 同 IP 登录尝试 | 60 次 / 分钟 | `ipMaxPerMinute` |
| 验证码有效期 | 5 分钟 | `smsCodeExpireSeconds` |
| 同号重发间隔 | 60 秒 | `smsResendSeconds` |
| 单个码的错误上限 | 错 5 次作废 | `smsMaxTries` |
| 同 IP 发码 | 30 条 / 小时 | `smsIpMaxPerHour` |
| 验证码调试回显 | dev 开、prod 关 | `echoSmsCode` |

**三个最容易做错的地方**：

1. **锁定期间即使密码正确也要拒绝**。否则攻击者「猜中了就进」，计数白算 ——
   锁定形同虚设。所以 `beforeAttempt()` 必须在验密码**之前**执行。
2. **失败计数只认凭证错误（401）**。参数格式错、账号被封禁都不计入 ——
   否则用户手滑打错一次格式就把自己锁了。
3. **验证码用后即焚**。校验通过立刻删，否则一个码能反复登录（重放）。

> 都是内存实现，重启即清空；多实例部署要换 Redis（见 §八）。
>
> IP 维度**只认 `remoteAddr`，不认 `X-Forwarded-For`**。原型阶段前面没有网关，
> 信 XFF 等于把限流开关交给调用方（请求头自己填就能绕）。
> 上生产要么在网关层限流，要么由网关**覆盖**写 XFF 之后再让后端读。

## 一、通用

### 健康检查
```
GET /api/health
→ data: "ok"
```

### 客户端登录（手机号 + 短信验证码）
```
POST /api/login
body: { "phone": "13800000001", "code": "482913" }
→ data: { user: {...}, token: "<JWT>", role: "client" }
```
> **验证码是真校验的**（v1.4 起）：必须先用 `/api/auth/sms-code` 拿码，
> 手机上收不到也没关系 —— dev 环境后端会把码回显在 `devCode` 里。
> 手机号不存在则自动注册。被封禁账号返回 403。token 的 role 是 `client`。

### 后台登录（admin / merchant 统一入口）
```
POST /api/auth/login
body: { "role": "admin" | "merchant", "account": "...", "password": "..." }
或   { "role": "merchant", "account": "<手机号>", "code": "482913" }
→ data: { token: "<JWT>", role, subject, shopId, name, expiresIn, shop? }
```

| role | 登录方式 | account 传什么 | 凭证 |
|---|---|---|---|
| `admin` | 账号密码 | `admin` | 密码 `admin123` |
| `merchant` | 账号密码 | 店铺 ID（`s_001`）**或**店内电话 | 密码 `123456` |
| `merchant` | 手机号 + 验证码 | **必须是手机号** | `/api/auth/sms-code` 下发的码 |

> `password` 与 `code` **二选一**：给了 `code` 就走短信验证码登录。
> 兼容：`account` 缺省时读 `phone`；`role` 缺省按 `merchant` 处理。
> 账号/密码错误统一回 **401 + 同一句提示**，不区分「账号不存在」和「密码错」，
> 防止把账号枚举出来。
> 商家登录会顺带返回 `shop` 视图，登录页可以直接显示「XX 小馆 · 审核中」。
> 被封禁的店登录返回 403。
>
> ⚠️ 演示密码（`admin123` / `123456`）**仅供原型** —— 密码登录是开发期的便利，
> 正式上线应让商家走短信验证码（接口已就绪，只差接短信网关）。
> 注意演示数据里商家的电话**有座机号**（如 `028-85456789`），
> 那种店不能用验证码登录，请用店铺 ID + 密码登。

### 发送短信验证码
```
POST /api/auth/sms-code
body: { "phone": "13800000001", "scene": "login" }
→ data: { sent: true, expiresIn: 300, resendAfter: 60, devCode: "482913"? }
```
> `devCode` **只在 `eatwhat.auth.echoSmsCode=true`（本地默认）时返回**，方便调试；
> 生产必须关掉，否则验证码跟着接口一起返回，等于没校验。
>
> 三道限流：同号 60 秒内不能重发、同 IP 每小时最多 30 条、验证码 5 分钟过期。
> 超限返回 **429**，提示里写明还要等多久。
>
> 短信发送走 `SmsSender` 接口，本地实现是 `DevSmsSender`（只打日志、不真发）。
> 接真实网关时新写一个实现即可，调用方一行都不用改。

### 文件上传
```
POST /api/upload            （multipart/form-data，字段名固定 file）
→ data: { url, relative, name, kind, size, sizeText, uploader }
```
> `url` 是**绝对地址**（`http://host:8080/uploads/20260916/xxx.png`）——
> 前端跑在 5173、后端在 8080，相对路径在页面里取不到。
> `kind` 为 `image` / `video`；图 5MB、视频 20MB 上限（配在 `eatwhat.upload.*`）。
>
> **四道校验，缺一不可**：
>
> | # | 校验 | 为什么 |
> |---|---|---|
> | 1 | 扩展名白名单 | `.html` / `.jsp` 传进静态目录就是一个存储型 XSS |
> | 2 | **魔数（文件头）** | 扩展名和 Content-Type 都是客户端说了算的，改个名就能绕 |
> | 3 | 尺寸上限 | 图片 5MB / 视频 20MB |
> | 4 | 落盘名由服务端生成（UUID） | 原始文件名含 `../../` 就是路径穿越 |
>
> 上传目录 `./uploads`，由 `WebConfig` 托管在 `/uploads/**`；已在 `.gitignore` 里。
> 需要 admin 或 merchant 身份。

## 二、客户端

### 0. 启动聚合（适配层专用，页面第一个调的就是它）
```
GET /api/client/bootstrap
→ data: { shops: [shopView], dishes: [dishView], comments: [commentView], config: { priceTiers, tasteTags, cuisines } }
```
- 一次性返回客户端各页面所需的全部基础数据
- **适配层靠它做「同步预加载」**：同步请求数直接等于页面白屏时长，所以必须聚合成一个
- 实测：聚合后 1 个请求 ≈ 270ms；早前分散拉取 14 个请求 ≈ 3.6s（慢 13 倍）
- ⚠️ 这里返回的必须是 **view**（`stats` 嵌套结构），不是数据库实体——实体是扁平的 `statXxx`，直接返回前端取不到值

### 1. 信息流
```
GET /api/client/feed?tab=nearby|random&city=成都市&browsed=d_001,d_002
                   &tiers=tier_mid,tier_high&tastes=麻辣
→ data: [ dishView, ... ]
```
- `tab=nearby`：按 **置顶 > 权重 > 距离 > 时间衰减** 排序，取每家店铺最新一条
- `tab=random`：随机序 + **排除 `browsed` 中已浏览的**
- `tiers` / `tastes` **可选**：传了就按条件出流（维度内 OR、维度间 AND）
- 内容不足 3 条时自动回捞旧内容补位，**但筛选态下不补位**
  —— 补位会把不符合条件的菜塞回来，筛选就形同虚设

**筛选态下的三点差异**：
1. 每家店取的是「**符合筛选条件的最新一条**」，而不是笼统的最新一条。
   否则筛「麻辣」时，某店最新菜不辣就会被整店剔除 —— 哪怕店里更早有辣的菜。
2. **不限 24h**。筛选是用户主动找东西，若只给 24h 内，小众条件会直接筛空。
3. **失效条件自动收敛**（前端本地逻辑，后端无需实现）：平台删掉一个价格档后，
   用户 `localStorage` 里还留着旧 id。前端读取筛选条件时用 `sanitizeFilter`
   自动剔除失效项 —— 否则顶部会显示「筛选：tier_old」这种原始 id，且永久筛空。
   App 端从本地缓存恢复筛选条件时，需要做同样处理。

> 前端目前的实现是：适配层已缓存全量数据，`buildFeed` 在**本地**算筛选
> （数据仍来自后端），省掉一次同步请求。后端这两个参数供未来 App 端使用
> —— App 不可能预加载全量数据。

### 2. 店铺详情
```
GET /api/client/shop/{shopId}
→ data: { ...店铺字段, dishes: [ dishView ] }
```

### 3. 店铺菜品列表
```
GET /api/client/shop/{shopId}/dishes
→ data: [ dishView ]
```

### 4. 菜品详情
```
GET /api/client/dish/{dishId}
→ data: dishView
```

### 5. 评论列表
```
GET /api/client/dish/{dishId}/comments
→ data: [ { id, userId, userName, avatar, content, at, reply: {content,at}|null } ]
```

### 6. 发表评论
```
POST /api/client/dish/{dishId}/comment
body: { "userId": "u_001", "content": "好吃" }
→ data: commentView
```
> 封禁用户返回 403。

### 7. 互动（点赞/收藏/打卡/浏览）
```
POST /api/client/dish/{dishId}/action
body: { "type": "like" | "favorite" | "checkin" | "view" }
→ data: null
```

### 8. 筛选（明细列表）
```
POST /api/client/filter
body: { "tiers": ["tier_mid"], "tastes": ["麻辣"] }
→ data: [ dishView ]
```
> 空数组表示不限。档位与口味之间是 **AND**，维度内部是 **OR**。
> 返回**全部**符合条件的菜品，**不做「每店一条」去重** —— 这是明细列表，
> 语义上等同于"搜索结果的替代品"（产品不做搜索）。
> 若要"每店一条"的筛选信息流，用 `GET /feed?tiers=..&tastes=..`。

### 9. 客户端配置
```
GET /api/client/config
→ data: { priceTiers: [...], tasteTags: [...] }
```

## 三、商家端

> 商家端 8 个页面**全部接后端读写**，写操作统一走适配层的 `MOCK.act(action, payload)`。
> **身份（v1.3 起）**：先 `POST /api/auth/login` 拿 JWT，适配层存进
> `localStorage` 并在每个请求带上 `Authorization: Bearer <token>`。
> **`shopId` 以 token 为准**，页面不许自己传 —— 传了和 token 不一致的会被 403 挡下。
> 登录后仍会写 `localStorage['merchantShopId']`，但那只用于**刷新页面时恢复身份**，
> 不再是授权的依据。
>
> 提醒：`/api/merchant/**` 全部需要 merchant token，**只有 `/api/merchant/apply` 公开**
> （还没账号的人才能提交入驻申请）。

### 0. 启动聚合（适配层专用，商家端页面第一个调的就是它）
```
GET /api/merchant/bootstrap?shopId=s_001
→ data: {
    shop,                                    // shopView，含 status / rejectReason / stats
    dishes: [...],                           // 本店**全部**菜品，含 status=removed
    comments: [...],                         // 本店菜品下的评论，额外带 dishName
    config: { priceTiers, tasteTags, cuisines, publishRule },
    canPostToday, cooldownSeconds, intervalHours, dailyLimit
  }
```
> ⚠️ **不能复用 `/client/bootstrap`**。那个接口给的是「客户端可见」的数据 ——
> 只含在营店铺、也不含 removed 菜品。商家一旦处于 `pending` / `rejected` 状态，
> 用它会让 `getShop` 直接返回 null、整页空白；下架的菜也会凭空消失，
> 而那恰恰是商家要处理的东西。

### 1. 工作台
```
GET /api/merchant/dashboard/{shopId}
→ data: { shop, canPostToday, cooldownSeconds, intervalHours, dailyLimit, dishes: [...] }
```

### 2. 发布前校验
```
GET /api/merchant/can-publish/{shopId}
→ data: { can: true|false, cooldownSeconds: 54000, status: "normal" }
```

### 3. 发布菜品
```
POST /api/merchant/dish
body: {
  "shopId": "s_001",
  "name": "麻婆豆腐",
  "type": "image",              // image | video，二选一
  "media": ["url1","url2"],
  "cover": "url",
  "desc": "简介≤100字",
  "price": 28,
  "tasteTags": ["麻辣"]
}
→ data: dishView
```
**服务端校验（按顺序）**：
1. 店铺未封禁、未禁言
2. 当日发布数 < `dailyLimit`
3. 距 `lastPublishAt` ≥ `intervalHours` 小时
4. 菜名非空
5. `type` ∈ {image, video}
6. media 非空；image 时 ≤ 9 张
7. 简介 ≤ 100 字
8. **`priceTierId` 由服务端按价格自动归档，客户端传的一律忽略**

### 4. 编辑菜品
```
PUT /api/merchant/dish/{dishId}
body: { name?, desc?, cover?, media?, price?, tasteTags? }
→ data: dishView
```
> 传了 `type` 且与库里不同 → 报错「内容形式发布后不可更改」。
> 改了 `price` → 自动重算 `priceTierId`。

### 5. 我的菜品
```
GET /api/merchant/dishes/{shopId}
→ data: dishView[]（含 status=removed 的）
```

### 6. 店铺信息
```
GET  /api/merchant/shop/{shopId}
PUT  /api/merchant/shop/{shopId}
body: { name?, cuisine?, intro?, address?, phone?, hours?, cover?, logo? }
```

### 7. 评论管理
```
GET    /api/merchant/comments/{shopId}      # 该店所有菜品下的评论，带 dishName
POST   /api/merchant/comment/{id}/reply     # body: { content }
DELETE /api/merchant/comment/{id}/reply     # 清除回评
```

### 8. 下架 / 恢复自己的菜品
```
POST /api/merchant/dish/{dishId}/remove     # body: { shopId }
POST /api/merchant/dish/{dishId}/restore    # body: { shopId }
→ data: dishView
```
> **逻辑下架**（`status=removed`），**不物理删除** ——
> 「超 24h 权重归零但不物理删除」是同一条口径。
> 带 `shopId` 会校验归属，商家下架别家的菜会拿到 403「只能操作本店的菜品」。
> 下架可逆，恢复即 `status=normal`。

### 9. 入驻申请
```
POST /api/merchant/apply
body: { name, phone, cuisine?, city?, district?, address?, hours?, intro?, cover?, logo?, lat?, lng? }
→ data: shopView（status = "pending"）
```
> 服务端三个必守点：
> 1. `status` 一律置 `pending`，不能直接上架 —— 平台审核这道闸门不能绕。
> 2. ⚠️ **`distance` 一律置 `null`**。给 0 会让它在「附近」排序里
>    插到所有真实店铺前面，白吃掉首页流量。
> 3. 发布规则取平台**当前**默认值（会随平台端改规则而变）。
> 必填 `name` / `phone`；提交时间自动写入 `submittedAt`。
> 提交后客户端**看不到**这家店（`listVisible` 排除 pending）。

> **`lat` / `lng`（v1.7 起）**：商家在地图上选的点会随申请一起入库，
> 但**此刻不参与任何排序** —— 待审店铺 `distance` 依然是 `null`。
> 坐标的权威化发生在**审核通过那一刻**（见下方 `audit/{id}/approve`）。
> 传空串 / `null` / 非数字一律按「没选点」处理（宽松解析，不抛 400）——
> 前端 input 空值会传 `""`，直接用 `Double.parseDouble` 会炸。

### 10. 审核通过（含地理闸门）
```
POST /api/admin/audit/{id}/approve
body: { reviewer?, force? }          # force 默认 false
→ data: shopView
```
> 通过时把商家选的坐标换算成 `distance` 落库（Haversine，到本市中心点），
> 这家店从此刻起才真正进入客户端「附近」排序。
>
> ⚠️ **没有有效坐标时默认拒绝**（400「该申请未提供有效坐标…」）。
> 加这道闸门是因为：distance 为 null 的店在排序里等同「无限远」，
> 悄无声息地上线会让运营以为「审核没生效」。
> 运营若确认要上线，传 `force: true` —— 此时 `distance` 保持 `null`
> （排末尾），**绝不**拿一个猜测值冒充权威距离。
>
> 前端对应交互：`admin/audit-shops.html` 的 `approve()` 发现没坐标时弹二次确认，
> 确认后才带 `force` 提交。

### 11. 店铺资料更新（含坐标重选）
```
PUT /api/merchant/shop/{shopId}
body: { name?, cuisine?, intro?, address?, phone?, hours?, cover?, logo?, lat?, lng? }
→ data: shopView
```
> ⚠️ **改了坐标必须重算 `distance`** —— 否则地图上挪了两公里，
> 客户端「附近」还按旧位置排，两边对不上。
>
> 判定条件：`lat` 和 `lng` **两个都传且与现值不同**才算「移动过」。
> 传半边（只给 lat）后端只覆盖那半边，**不做重算** ——
> 那会落到 `(新lat, 旧lng)` 这个不存在的位置。防护在适配层：
> `merchant.shop.update.local` 只认成对出现的坐标。

## 四、平台端

> 平台端 8 个页面**全部接后端读写**。页面里的写操作统一走适配层的
> `MOCK.act(action, payload)`：在线时同步 XHR 落库并回写内存，离线时只改内存。
> 所以「平台端点一下 → 客户端立刻变」这条链路是通的。
>
> **身份（v1.3 起）**：`/api/admin/**` 全部需要 **admin token**
> （`POST /api/auth/login` + `role=admin`）。未登录访问 `admin/*.html`
> 会被适配层引导回 `admin/login.html`。

### 0. 启动聚合（平台端适配层专用）

```
GET /api/admin/bootstrap
→ data: {
    overview:      { ...同 /admin/overview },
    shops:         [shopView],    # 全量（含待审核 / 已驳回 / 封禁）
    dishes:        [dishView],    # status=normal
    removed:       [dishView],    # status=removed
    reports:       [report],
    users:         [userView],    # 已按被举报次数倒序
    pendingShops:  [shopView],    # status=pending
    approvedShops: [shopView],    # status ∈ {normal, muted, banned}
    rejectedShops: [shopView],    # status=rejected
    config:        { priceTiers, tasteTags, cuisines, publishRule }
  }
```

- 平台端要用 **10 份**数据，分散就是 10 次同步请求，首屏会卡到没法演示
- ⚠️ 必须返回 **view**，不能返回实体 —— 实体是扁平字段（`statViews`），
  前端读嵌套（`shop.stats.views`），直接返回实体页面只会静默空白

### 数据概览

```
GET /api/admin/overview
→ data: {
    shopCount,                                  # 店铺总数（含待审核 / 已驳回）
    shopNormal, shopMuted, shopBanned, shopPending,
    dishCount, userCount, reportPending,
    dishToday,                                  # 当日 0 点起算（Asia/Shanghai）
    trend: [ { d: "周三" | "今日", v: 3 }, ... ]  # 近 7 日发布趋势，给柱状图
  }
```

> ⚠️ **KPI「在营店铺」= `shopNormal + shopMuted`，不是 `shopCount`。**
> `shopCount` 含待审核和已驳回的店，直接拿来当在营数会虚高（9 而非 6）。

### 商家审核（状态机）

```
GET  /api/admin/audit/pending            → data: [shopView]   # 待审核队列
POST /api/admin/audit/{id}/approve       body: { reviewer? }
POST /api/admin/audit/{id}/reject        body: { reason, reviewer? }
```

**状态机**：

```
            ┌──────────── approve ──────────┐
pending ────┤                               ├──→ normal
            └──────────── reject ──────────┘       （已上线，客户端可见）
                     │
                     ↓
                 rejected（已驳回，客户端不可见）
```

- **只审店铺，不审菜品**（冻结规则）。审核通过 = 店铺上线，客户端立刻可见
- `reject` 的 `reason` 为空 → 400
- 非 `pending` 状态再审核 → 400
- 审核痕迹字段：`submittedAt` / `reviewedAt` / `reviewer` / `rejectReason`
- `listVisible()`（客户端用）排除 `banned` / `pending` / `rejected`

### 店铺管理

```
GET  /api/admin/shops                   # 全量（含待审核、已驳回 —— 平台端必须看得到全部）
POST /api/admin/shop                    # 新增（审核通过后落库）
POST /api/admin/shop/{id}/mute          # 禁言
POST /api/admin/shop/{id}/ban           # 封店
POST /api/admin/shop/{id}/restore       # 解禁/恢复
POST /api/admin/shop/{id}/rule          # body: { intervalHours, dailyLimit }
```

### 推荐排名

```
GET  /api/admin/ranking?city=成都市
→ data: [shopView]（已按 置顶 > 权重 > 距离 > 时间衰减 排序）

POST /api/admin/ranking/order
body: { "shopIds": ["s_005","s_001","s_003"] }
→ data: [shopView]（重排后的完整列表，前端直接拿它重置本地顺序）
```
> 按数组顺序重写权重：`weight = total - index`。
> ⚠️ 返回的必须是**排过序**的列表 —— 早前返回 `listAll()`（未排序），
> 拖拽保存后顺序会弹回去，是踩过的坑。
> 排序时**置顶优先于权重**，所以置顶店即使权重低也会在最前。

### 置顶 / 权重

```
POST /api/admin/shop/{id}/pinned    body: { pinned: true }
POST /api/admin/shop/{id}/weight    body: { weight: 88 }
```

### 内容管理

```
GET  /api/admin/contents
→ data: { all: [dishView], removed: [dishView], reports: [report] }

POST /api/admin/dish/{id}/real-tag  body: { realTag: "real"|"ad"|"pending" }
POST /api/admin/dish/{id}/status    body: { status: "normal"|"removed" }

POST /api/admin/report/{id}/handle  body: { action: "confirmed"|"rejected" }
   confirmed + type=dish    → 自动下架该菜品
   confirmed + type=comment → 自动下架该评论
```
> **下架不是物理删除**（冻结规则）。超 24h 内容权重归零但不删。

### 用户管理

```
GET  /api/admin/users                 # 按被举报次数倒序（首位是 u_003，不是 u_001）
POST /api/admin/user/{id}/status      body: { status: "normal"|"warned"|"banned" }
```
> 被举报次数 ≥ 3 时，`incReport` 会自动将其状态置为 `warned`。
> **封号不删除历史评论**（冻结规则）。

### 平台配置

```
GET  /api/admin/config
→ data: { priceTiers, tasteTags, cuisines, publishRule }

POST /api/admin/config/publish-rule
body: { "intervalHours": 24, "dailyLimit": 1 }
→ data: { intervalHours, dailyLimit }
```
> 全局默认发布规则。它决定**新店铺的初始值**，也是单店「自定义」标记的比较基准。
> 按冻结规则 9：改规则**不影响已发记录**，从下次发布算起。

```
POST /api/admin/config/price-tiers
body: { "tiers": [ {"id":"tier_mid","name":"中等","min":0,"max":50}, ... ] }
→ data: { priceTiers: [...], recalculated: 3, dishes: [dishView] }
```
> **保存后自动重算所有菜品档位**，`recalculated` 是变更数量。
> 兑现「商家只填价格、系统自动归档、不可手选档位」。
> 区间无上限用 `max: -1` 表示（JSON 无法存 Infinity）。
> 顺带回传 `dishes`（档位变了菜品也变），省掉前端一次请求。

```
POST /api/admin/config/taste-tags   body: { tags: ["麻辣",...] }      → data: [String]
POST /api/admin/config/cuisines     body: { cuisines: ["川菜",...] }  → data: [String]
```

## 六、前端接入方式

适配层 `assets/js/api.js` 已注入全部 23 个页面。切换方式：

```js
// 启用后端
localStorage.setItem('useApi', '1');
location.reload();

// 回到本地假数据
localStorage.removeItem('useApi');
location.reload();

// 后端不在 8080 时改地址
localStorage.setItem('apiBase', 'http://192.168.1.10:8080/api');
```

适配层**保持与 `MOCK` 相同的同步函数签名**，所以页面代码无需改动。
后端未启动时自动降级回本地假数据，原型永远能打开。
⚠️ 适配层必须**立即 install**，不能等 `DOMContentLoaded` —— 页面脚本是同步执行的。

### 写操作：`MOCK.act(action, payload)`

三端所有写操作统一走这一个入口（`assets/js/api.js` 的 `ACTIONS` 字典）：

```js
MOCK.act('shop.ban', { id: 's_001' });
MOCK.act('audit.approve', { id: 'p_001' });
MOCK.act('config.priceTiers', { tiers: [...] });
```

每个 action 定义四项：

| 字段 | 作用 |
|---|---|
| `path` | 后端路由（在线时用） |
| `body` | 请求体构造 |
| `apply` | 成功后**回写内存**，让页面立刻刷新而不必重拉 |
| `local` | 离线时的等价本地操作，保证原型照样能演示 |

已注册的 action：

```
# 平台端
audit.approve / audit.reject
shop.mute / shop.ban / shop.restore / shop.rule / shop.pinned / shop.weight
ranking.order
dish.status / dish.realTag
report.handle
user.status
config.priceTiers / config.tasteTags / config.cuisines / config.publishRule

# 商家端
merchant.publish / merchant.dish.update
merchant.dish.remove / merchant.dish.restore
merchant.shop.update
merchant.comment.reply / merchant.comment.clearReply
merchant.apply
```

> 商家端 action 的 `shopId` **一律由适配层的 `merchantShopId()` 决定**，
> 不接受页面随便传 —— 页面把参数写错就能改到别家店的数据，这种口子不能留。
> 服务端在 remove / restore 上还会再校验一次归属（403）。

返回 `false` 表示动作失败（后端拒绝或网络异常），页面据此弹错误提示。
`MOCK.isOnline()` / `EAT_API.isOnline()` 可查当前是否真的连着后端；
`MOCK.preloadSync()` 供页面手动重拉（商家端审核页的「刷新审核状态」用它）。

### 按端识别数据源

适配层按 `location.pathname` 判断当前端，只拉对应端的启动聚合接口：

| 端 | 路径前缀 | 聚合接口 |
|---|---|---|
| 客户端 | `client/` | `GET /api/client/bootstrap` |
| 商家端 | `merchant/` | `GET /api/merchant/bootstrap?shopId=<身份>` |
| 平台端 | `admin/` | `GET /api/admin/bootstrap` |

**商家身份从哪来**：登录 `/api/auth/login` 拿 token，适配层把会话写进
`localStorage`（`eatwhat_token` / `eatwhat_role` / `eatwhat_shopId` 等）。
之后适配层的 `merchantShopId()` 一律读会话里的 `shopId`，读不到才回退到
`MOCK.currentMerchant.shopId`。**页面不许自己传 shopId**，服务端以 token 为准。
入驻申请（`merchant.apply`）成功后把待审店铺 ID 存在 `sessionStorage['pendingShopId']`，
不写身份 —— 店还没过审，不算登录态。

### 登录态与上传（适配层 API）

```js
MOCK.login(role, account, password)  // 成功落会话，失败返回 false
MOCK.logout()                        // 清会话
MOCK.isLoggedIn()                    // 本地是否还有未过期 token
MOCK.upload(file)                    // 返回 Promise<{url, kind, size, ...}>
```

- 请求头由适配层统一加 `Authorization: Bearer <token>`，页面不用管。
- **遇到 401 会自动清会话并引回登录页**；`doRequest` 只在 401 时重试一次，
  避免死循环。
- 后端没启动时 `MOCK.upload` 降级为 `FileReader` → **dataURL**，
  原型照样能预览图片，只是不落盘。
- 登录页（`admin/login.html`、`merchant/login.html`）会被适配层
  **跳过启动预加载** —— 那时候还没有 token，预加载必然 401。

⚠️ 三端的数据口径**故意不同**，不要互相复用：
- 客户端 bootstrap 只给「客户端可见」的店（排除 pending / rejected / banned）
- 商家端 bootstrap 给「我这一个店」的全量数据，**含 pending / rejected 的自己**和 **removed 的菜**
- 平台端 bootstrap 给全量店铺 + 审核队列 + 举报 + 用户

## 七、演示数据（种子数据）

**唯一数据源是 `server/.../config/DataSeeder.java`**，H2 内存库启动时灌入。

| 集合 | 数量 | 说明 |
|---|---|---|
| 店铺 | **29** | 在线 22 / 待审核 5 / 已驳回 2 |
| 菜品 | **54** | 在架 52 / 已下架 2（对应 status=confirmed 的菜品举报） |
| 用户 | **14** | 按被举报次数倒序，首位 `u_003`（reports=5） |
| 评论 | **28** | 含商家回评 |
| 举报 | **9** | 待处理 5 |

**几条刻意为之的设计**：

1. **菜品的发布时间锚定「今天 0 点」往前推 N 天**，而不是「当前时刻往前推 N 小时」。
   后者在凌晨启动会让「今日发布数」变成 0、趋势图跟着错位。
   落在未来的时间戳会被 clamp 到当前时刻。
2. **趋势图近 7 天每天都有内容**（5/7/6/6/8/9/11）。某天为 0 会让柱子看起来像坏了。
3. **店铺的 `lastPublishAt` / `canPostToday` 由「该店最新一条菜品」反推**，
   不手写 —— 否则会出现「菜品是今天发的、店铺却显示三天没发」的矛盾。
   `canPostToday` 同时考虑「间隔未到」和「今日条数已满」。
4. **权重刻意并列**。并列时排序才会走到「距离」和「时间衰减」两级；
   权重全不相同的话，后两级规则永远演示不出来。
5. **`priceTierId` 由 `ConfigService.resolveTier(price)` 算出**，不手写，
   保证与平台配置的区间永远一致。
6. **待审核 / 已驳回店铺的 `distance` 是 `null`**。给 0 会被排序当成
   「就在你脚下」，把还没上线的店顶到推荐榜首。
   （坐标本身有值 —— 是商家选的点，只是不算距离。见「审核通过」一节。）
7. **全部店铺同一个城市**。前端 `buildFeed` 是本地实现、不按城市过滤，
   加第二个城市会造成「客户端刷得到、App 端 feed 刷不到」的分叉，
   还会让客户端可刷内容变少。城市维度留给 `/admin/ranking?city=` 参数。
8. ⚠️ **在线店铺的 `distance` 不手写，由坐标推导**
   （`DistanceCalculator.toCityCenter`）。早先手写过一份，
   22 家里有 21 家和公式算出来的对不上，最大差 6.7km ——
   演示时列表排序是一种结果、商家改个位置再刷新又是另一种，很像排序坏了。
   现在 `ShopSeed` 里**没有 distance 字段**，全靠 `lat/lng + city` 现算。
9. ⚠️ **待审核店铺走真实入驻接口建立**（`merchantController.applyPending`），
   不是手搓字段。确保「演示的待审」和「真实入驻的待审」口径一致。
   代价：接口先落一条 `s_<时间戳>`，脚本要换成 `p_00X` 稳定 id。
   **换 id 必须先存新的再删旧的** —— JPA 认为 id 变了就是另一个实体，
   直接 `setId() + save()` 会 INSERT 出第二条，待审列表每条都翻倍
   （页面不报错，只是列表莫名变长）。

**离线原型怎么同步**：`assets/data/mock.js` 的数据段由

```bash
python dev.py --api-only              # 另开终端把后端跑起来
python server/tools/export_mock.py    # 幂等，可重复跑
```

从后端导出生成。**不要手改 mock.js 的数据段**，会被下次导出覆盖。

导出的两点取舍：
- `decay` **不导出** —— 它是「请求那一刻」的瞬时值，写进静态文件就成了冻结的
  假数据；前端用本地 `timeDecay(publishedAt)` 现算。
- `priceTiers` 的 `max: -1`（后端表示「无上限」，因为 JSON 存不了 Infinity）
  导出时换成 `Infinity`，对齐前端语义。
