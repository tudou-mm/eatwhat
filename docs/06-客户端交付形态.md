# 06 · 客户端交付形态（用户端 = 手机产品）

> **前提澄清（很重要）**：用户端**本来就是手机端产品** —— 是在手机上刷附近新菜的。
> 规格书 §3「客户端双形态」说的「桌面下居中手机外壳 + 侧栏说明卡」，
> 那是**开发期在电脑上预览时的展示方式**，不是产品的交付形态。
>
> 所以这一份要回答的不是「什么时候把客户端搬到手机」，
> 而是：**一个手机产品，用什么形态交付给用户。**

---

## 1. 把问题摆正

三端的产品性质本来就不一样，交付形态也应该不一样：

| 端 | 谁用 | 在什么设备上用 | 交付形态 |
|---|---|---|---|
| **客户端** | 食客（公众） | **手机**，扫码/搜索进来，用得随意 | **手机产品** —— 必须能装、能定位、打开就是 App 样子 |
| **商家端** | 店主/店员 | 多在**电脑**上，也可能手机看 | 网页即可，桌面优先、手机可用 |
| **平台端** | 你自己/运营 | **只有电脑** | 网页，桌面专用 |

**所以真正要决策的只有客户端。** 商家端和平台端用网页是对的，不用动。

而客户端要的「手机产品」，按「拿到多少原生能力」从小到大排：

| 方案 | 交付物 | 用户怎么拿到 | 定位 | 推送 | 上架 | 工作量 |
|---|---|---|---|---|---|---|
| **A. 手机网页**（现状） | 一个网址 | 输网址/扫码 | ❌ **http 下直接被拒** | ❌ | — | 0 |
| **B. PWA**（推荐先做） | 一个网址 → 装到主屏 | 打开网址 →「添加到主屏幕」 | ✅ **需 HTTPS** | ⚠️ 有限 | ❌ | **小** |
| **C. Capacitor 套壳**（要上架再做） | `.apk` / `.ipa` | 应用商店下载，或直接装包 | ✅ 原生 | ✅ 完整 | ✅ | **中** |
| D. 原生/RN/Flutter 重写 | 重做 | 应用商店 | ✅ | ✅ | ✅ | **极大** |

**结论：A → B → C 顺着走，不需要 D。**
你现在的代码是 **23 页纯静态 + 零构建工具 + 零 ES module**，
B 和 C 都是吃这套静态资源的，**一行业务代码都不用改**，而且 B 的产出 C 能直接复用。

### ✅ 好消息：客户端的响应式层已经做对了

规格书 §3 说的「桌面下居中手机外壳 + 侧栏说明卡 / 移动端全屏」，
在 `client/` 6 个页面里都已实现（`@media (max-width: 820px)`，见各页内联样式）：

```css
@media (max-width: 820px) {
  .stage { padding: 0; }
  .side-note { display: none; }        /* 开发说明卡隐藏 */
  .phone { width: 100vw; height: 100vh; border-radius: 0; border: none; }
  .phone__notch { display: none; }     /* 假刘海隐藏 */
}
```

**也就是说：手机上打开，界面已经是全屏的、没有手机外壳。**
所以剩下的工作**不是改样式**，而是补三样「网页没有、手机产品必须有」的东西：

1. **HTTPS** —— 否则定位拿不到（核心）
2. **manifest** —— 否则装不到主屏
3. **Service Worker** —— 否则弱网/断网打不开

这恰好就是 PWA 三件套，也正好解释了为什么它是最小的补齐动作。

## 2. ⚠️ 最要紧的一件事：**没有 HTTPS 就没有定位**

用户端是手机产品，而**手机产品最核心的能力就是「附近」** ——
「附近」靠定位，定位靠 HTTPS。所以这条不是技术细节，**它直接决定产品能不能用**。

浏览器出于安全考虑，只在**安全上下文**下才给定位：

| 环境 | 定位能用吗 | 说明 |
|---|---|---|
| `file://` 直接双击打开 | ❌ | 连 `localStorage` 都受限 |
| `http://192.168.x.x:5173`（手机连你电脑） | ❌ | **明文 http 一律拒绝** |
| `http://localhost:5173` | ✅ | `localhost` 是特例，所以**你在电脑上测是好的** |
| `https://xxx.com` | ✅ | 唯一能在真手机上用定位的方式 |

**这就是为什么「手机上打开看着正常，就是定位不动」。**
`assets/js/user-loc.js` 第 35 行已经把这个结论写在注释里了，
目前会优雅降级到「距市中心」并给黄灯提示 —— **不会白屏，但也永远拿不到真位置**。

> 🔴 **所以：手机上想用定位，必须先有一个 HTTPS 地址。这是硬门槛，绕不过去。**

## 3. 方案 B：PWA（推荐先做）

> **只有客户端要装 PWA。** 商家端/平台端是网页，不用加这些 —— 别一股脑给 23 个页面都塞。
> 要改的只有 `client/` 下的 6 个页面。

### 3.1 要加的三个文件

```
assets/
  manifest.webmanifest      ← 新增：应用名、图标、主题色、启动方式
  sw.js                     ← 新增：Service Worker（离线缓存）
  icons/                    ← 新增：192/512 图标
client/*.html               ← 6 个页面 <head> 各加 4 行（见下）
```

**① `assets/manifest.webmanifest`**

```json
{
  "name": "吃什么 · 附近新菜",
  "short_name": "吃什么",
  "start_url": "/client/feed.html",
  "scope": "/",
  "display": "standalone",
  "background_color": "#121212",
  "theme_color": "#FE2C55",
  "orientation": "portrait",
  "icons": [
    { "src": "/assets/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/assets/icons/icon-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/assets/icons/icon-512-maskable.png", "sizes": "512x512",
      "type": "image/png", "purpose": "maskable" }
  ]
}
```

> ⚠️ `display: "standalone"` 是关键 —— 有它才会**隐藏浏览器地址栏**，看着才像 App。
> ⚠️ `maskable` 图标是安卓自适应图标的必需项，缺了会被切成奇怪形状。
> ⚠️ `start_url` 指到**客户端首页**（食客才是主要用户），不是三端任选一。

**② 每个页面 `<head>` 里加这 4 行**

```html
<link rel="manifest" href="/assets/manifest.webmanifest">
<meta name="theme-color" content="#FE2C55">
<link rel="apple-touch-icon" href="/assets/icons/icon-192.png">
<meta name="apple-mobile-web-app-capable" content="yes">
```

> ⚠️ 路径必须是**根绝对路径** `/assets/...`。写相对路径 `assets/...` 在
> `/merchant/apply.html` 下会解析成 `/merchant/assets/...` → 404，
> 而这个问题**在电脑上完全看不出来**（根路径页面正常）。
> —— 本项目在「高德 Key 配置文件」上已经踩过一次同样的坑。

**③ `assets/sw.js` —— 只缓存静态资源，别碰接口**

```js
const CACHE = 'eatwhat-v1';
const SHELL = [
  '/client/feed.html', '/client/dish.html', '/client/shop.html',
  '/assets/css/base.css', '/assets/js/api.js', '/assets/js/user-loc.js',
  '/assets/data/mock.js', '/assets/manifest.webmanifest'
];

self.addEventListener('install', e => {
  e.waitUntil(caches.open(CACHE).then(c => c.addAll(SHELL)).then(() => self.skipWaiting()));
});
self.addEventListener('activate', e => {
  e.waitUntil(caches.keys().then(ks =>
    Promise.all(ks.filter(k => k !== CACHE).map(k => caches.delete(k)))
  ).then(() => self.clients.claim()));
});
self.addEventListener('fetch', e => {
  const u = new URL(e.request.url);
  // ⚠️ 接口一律走网络，不缓存 —— 缓存了会看到「昨天的菜」。
  if (u.pathname.startsWith('/api/')) return;
  // 只处理同源静态资源
  if (u.origin !== location.origin) return;
  e.respondWith(
    caches.match(e.request).then(hit =>
      hit || fetch(e.request).then(res => {
        const copy = res.clone();
        caches.open(CACHE).then(c => c.put(e.request, copy));
        return res;
      }).catch(() => caches.match('/client/feed.html'))
    )
  );
});
```

> ⚠️⚠️ **`/api/` 必须直通，绝不能缓存。** 信息流是「今天的菜」，
> 缓存后会出现「明明刷新过还是昨天那批」——而且看起来像后端坏了。
> ⚠️ 版本号 `eatwhat-v1` 改名即强制更新，改静态资源后记得改。
> ⚠️ **不要**给 `/api/` 加离线兜底返回假数据 —— 会让「后端没起」被伪装成正常。

**④ 注册 SW（放在 `api.js` 之后，或所有页面统一引一个小 `pwa.js`）**

```html
<script>
if ('serviceWorker' in navigator && location.protocol === 'https:') {
  // ⚠️ 只在 https 下注册：localhost 上注册会缓存住旧文件，
  //    开发时改了代码刷不出来，非常烦。
  navigator.serviceWorker.register('/assets/sw.js');
}
</script>
```

### 3.2 部署：怎么拿到 HTTPS 地址

有三个选择，按「省事程度」排序：

| 方式 | 地址长啥样 | 成本 | 适合 |
|---|---|---|---|
| **Cloudflare Tunnel（推荐）** | `https://eatwhat-demo.trycloudflare.com` | 免费、一条命令 | 立刻给手机看 / 发给朋友 |
| **Vercel / Netlify / Cloudflare Pages** | `https://eatwhat.vercel.app` | 免费 | 纯静态够用，但**后端要另找地方** |
| **自己买服务器 + 域名 + 证书** | `https://你的域名.com` | 域名约 ¥30/年 + 服务器 | 正式试点 |

**Cloudflare Tunnel 最快**（后端也能一起暴露，因为是反代整台机器）：

```bash
# 装 cloudflared 后，一条命令把本地 8080(后端) + 5173(前端) 暴露出去
# 注意：两个端口要分别开隧道，或者干脆让后端把静态文件一起托管
cloudflared tunnel --url http://127.0.0.1:5173
```

> ⚠️ **但这样后端还是 `http://localhost:8080`，手机上打不通** —— 手机上的
> `localhost` 指的是手机自己。所以要么后端也开隧道，要么**让 Spring Boot 直接把
> 前端静态文件一起托管**（更推荐，见 §3.3）。

### 3.3 让后端顺带托管前端 —— ✅ **已完成（v1.9）**

> 这一节原本写的是「建议」。**v1.9 已经做完并实测通过**，下面记结论与踩过的坑，
> 供后续维护参考。

现在前端和接口是同一个地址：`:8080` 同时发页面和 `/api`。

```java
// server/src/main/java/com/eatwhat/config/WebConfig.java
private void mountStatic(ResourceHandlerRegistry registry, String dir) {
    Path root = Paths.get(dir).toAbsolutePath().normalize();
    Path[] subs = { root.resolve("client"), root.resolve("merchant"),
                    root.resolve("admin"), root.resolve("assets") };
    for (Path p : subs) {
        if (!Files.isDirectory(p)) continue;
        String name = p.getFileName().toString();
        registry.addResourceHandler("/" + name + "/**")
                .addResourceLocations(p.toUri().toString())
                .setCacheControl("assets".equals(name)
                        ? CacheControl.maxAge(1, TimeUnit.HOURS)
                        : CacheControl.noCache());
    }
}
```

前端目录位置由 `application.yml` 的 `web.dir` 决定（默认 `..`，相对后端运行目录 `server/`）：

```yaml
web:
  dir: ..
```

改完之后：

- 手机访问 `<任意地址>/client/feed.html` —— **一个地址搞定，同源无跨域**
- `api.js` 里 `API_BASE` 是 `/api`（同源相对路径），**跨域问题彻底消失**
- `dev.py` 的 5173 只留给你本地开发用，不再是对外依赖
- 根路径 `/` 自动 302 到 `/client/feed.html`

#### ⚠️ 四条踩过的坑

**① 静态映射只挂四个确定前缀，绝不写 `/**`。**
写 `/**` 会把 `/api/**` 也吃进去 —— 而且是**可能只坏一半**（部分接口仍正常）那种最难查的坏法。

**② HTML 不能长缓存，静态资源可以。**
HTML 一旦被缓存，**改了页面、手机上却还是旧的，刷新也不管用**。
但 `setCachePeriod(0)` 实测落到 `Cache-Control: no-store`（完全禁缓存），
**不是**想要的「每次回源校验」。正解是 `CacheControl.noCache()`，
配合 `Last-Modified` 无改动时会回 **304**。

**③ 🔴 `API_BASE` 绝不能写死 `http://localhost:8080`。**
**手机上的 `localhost` 指的是手机自己。** 写死了**在电脑上一切正常**，
到了手机上却永远连不上 —— 这类 bug 开发期完全看不出来。
判断用**排除法**（`api.js` 的 `defaultApiBase()`）：

| 情况 | 返回 |
|---|---|
| `location.port === '5173'`（dev server） | `http://localhost:8080/api` |
| `location.protocol === 'file:'` | `http://localhost:8080/api` |
| **读不到 `location.port`**（沙箱/非浏览器） | `http://localhost:8080/api` |
| 其余（页面由后端发出） | **`/api`** |

最后那一支**不能省**：`test_adapter.cjs` 的 `location` 替身只有 `{search, href}`，
**没有 `port`/`protocol`**，去掉它会**让适配层 27 项掉到 20 项**。
→ **默认值要偏向「能用」而不是「正确」。**

**④ 缺页必须是 404 而不是 500。**
后端开始发页面之后，「这个页面不存在」会走 `NoResourceFoundException`，
被 catch-all 兜成 **500 + Spring 原始措辞**（`No static resource xxx.`）——
既误导用户（以为服务器挂了）又污染日志。已在 `GlobalExceptionHandler` 单独处理。

> ⚠️ 生产部署时 `web.dir` 要指向前端文件的实际位置（例如 `/var/www/eatwhat`），
> 或者把静态文件打进 jar 用 `classpath:`。目录不存在只打日志跳过，**不会导致启动失败**。

### 3.3.1 没有服务器 / 域名 / 证书时怎么给手机试

**这是本机当前的真实处境**（用户明确说「https 没进行部署」）。
按门槛从低到高三条路：

**① 临时 HTTPS 隧道 —— 推荐，今天就能试**

```bash
python tools/tunnel.py
```

零安装、零注册（`ssh -R` 走 `localhost.run`，Windows 自带 ssh），
跑完打印 `https://xxxx.lhr.life/client/feed.html`，手机直接打开。

> ⚠️ **这是唯一能让手机用上「定位」的免部署办法** ——
> 因为浏览器只在 HTTPS（或 localhost）下给定位。
> ⚠️ 域名临时，Ctrl+C 即失效；流量经过第三方，**别放敏感数据**。
> ⚠️ 脚本自己生成专用密钥 `~/.ssh/eatwhat_tunnel_ed25519`，
> **不动用户已有的 SSH 身份密钥**（越权使用 + 新机器上往往根本没有私钥）。

**② 局域网** —— 手机连同一 Wi-Fi，访问 `http://<电脑IP>:8080/client/feed.html`。
页面能看，**但定位一定不可用**（`http://` 下浏览器直接拒绝）。

**③ 正式部署** —— 有服务器/域名/证书之后：`mvn package` → Nginx/Caddy 反代 + 证书 →
调 `web.dir`。见上方 §3.2 的对比表。

### 3.4 PWA 能拿到什么 / 拿不到什么

| 能力 | PWA | 说明 |
|---|---|---|
| 装到主屏、全屏无地址栏 | ✅ | 安卓/鸿蒙是「安装应用」，iOS 是「添加到主屏幕」 |
| **定位** | ✅ | **前提是 HTTPS**，这是最大的收益 |
| 离线看已加载页面 | ✅ | SW 缓存 |
| 相机（拍菜品照） | ✅ | `<input type="file" accept="image/*" capture>` |
| **系统推送通知** | ⚠️ | **iOS 16.4+ 且要先装到主屏**才支持；安卓 Chrome 支持 |
| 后台定位 | ❌ | 浏览器不给，必须原生 |
| 上应用商店 | ❌ | PWA 进不了 App Store / 华为小米应用市场 |
| 读取本机相册原图 | ⚠️ | 需要用户手动选 |

### 3.5 iOS 的两个大坑（必须知道）

1. **iOS 只能用 Safari 安装 PWA。** 用微信 / Chrome 打开「添加到主屏幕」装出来的
   只是个书签，**不会全屏、没有推送**。
   → 用户引导文案要写清楚：「请用 Safari 打开 → 分享 → 添加到主屏幕」。
2. **iOS 的 PWA 有 7 天「保鲜期」。** 如果用户 7 天没打开，`localStorage` 和缓存会被
   系统清掉 —— 本项目互动/浏览/打卡**存在 `localStorage`**，会被一起清掉。
   → 这正是二期要挪到后端的理由（见 §5）。

## 4. 方案 C：Capacitor 套壳（要上架时再做）

### 4.1 为什么是 Capacitor 而不是 Cordova / RN

| 方案 | 对现有代码的改造 | 说明 |
|---|---|---|
| **Capacitor（推荐）** | **几乎为零** | 它就是个「WebView 壳」，喂它一个静态目录即可。你的 23 个 HTML **原样放进去就能跑** |
| Cordova | 小 | 生态老了，新项目不推荐 |
| React Native / Flutter | **重写** | 23 个页面全废，等于重做 |

**Capacitor 对你这套代码是天然契合的**：没有构建步骤、没有 ES module、
全是静态文件 —— 正好是它最喜欢的形式。

### 4.2 大概怎么做（示意，不是现在就要做）

```bash
npm i @capacitor/core @capacitor/cli
npx cap init eatwhat com.tudou.eatwhat --web-dir=www
mkdir -p www && cp -r client merchant admin assets www/   # 静态文件搬进 www
npx cap add android && npx cap add ios
npx cap sync
npx cap open android      # 用 Android Studio 出 apk
npx cap open ios          # 用 Xcode 出 ipa
```

**装两个插件补齐 PWA 的短板：**

```bash
npm i @capacitor/geolocation @capacitor/push-notifications
```

### 4.3 相对路径是唯一的雷

套壳后页面路径协议会从 `http://` 变成 `capacitor://localhost`（iOS）或
`https://localhost`（安卓），**根绝对路径 `/assets/...` 会失效**。

→ **建议**：打包前把 23 个页面里的 `/assets/` 统一改成 `../assets/`
（或引入一个 `BASE` 变量）。**这一步现在就可以先不做**，
等真要打包时用一个脚本批量替换即可 —— 因为现在 `API_BASE` 已经是相对可配的。

> ⚠️ 别用「根绝对路径」写死任何东西。本项目在 `amap-key.js` 上已经踩过：
> 写相对路径在子目录下 404，写根路径在套壳后 404。**两头都要能活，只能靠变量。**

### 4.4 iOS 上架的硬门槛

| 项 | 成本 | 说明 |
|---|---|---|
| Apple 开发者账号 | **$99/年** | 个人号，必须 |
| 审核 | 1～3 天，可能被拒 | 纯 WebView 壳**会被拒**（Guideline 4.2 最低功能性） |
| 安卓各商店 | 免费～¥200 | 华为/小米/OPPO/vivo 各有各的审核 |
| 备案 | 国内上架必须 | 服务器需在境内且已 ICP 备案 |

> 🔴 **「纯 WebView 壳」过不了 App Store 审核。** 4.2 条款要求 App 有
> 「超越网页的功能」。所以要走上架这条路，**必须至少加一两项原生能力**
> （推送、相机、离线数据、签到 GPS）——这也是为什么 §4.2 要装那两个插件。
>
> **如果不上架、只是自己人用**：安卓可以打 apk 直接装（无需审核），
> iOS 可以走 **TestFlight**（100 个测试员，无需审核）或 **企业签名**。
> 这是当前阶段最现实的路。

## 7. 一句话回答「怎么弄」

> 用户端本来就是手机产品，所以问题不是「要不要上手机」，而是**用什么形态交付**：
> 现在把客户端 6 个页面接上 **PWA**（三个文件 + 一个 HTTPS 地址），
> 手机上立刻就能装成 App、**定位真正可用**；
> 等要上架商店时，再用 **Capacitor** 把同一份代码套成 `.apk` / `.ipa`。
> 因为你现在是**纯静态 HTML、零构建、零 ES module**，两条路都不用改业务代码。
>
> 唯一的硬门槛是：**没有 HTTPS，就没有定位。**

## 附：为什么不用「响应式改一改」

既然客户端**本来就是手机端**，最自然的问题就是：现在 `viewport` 已经配好了、
手机打开也能看，是不是改改 CSS 就够了？

**不够。** 因为「手机上能看」和「是个手机产品」差的不是样式，是四条能力：

| | 响应式网页 | PWA |
|---|---|---|
| **定位（核心）** | ❌ 明文 http 下浏览器直接拒绝 → **「附近」是假的** | ✅ 有 HTTPS 就能拿到真位置 |
| 安装 | ❌ 每次都要输网址/找二维码 | ✅ 添加到主屏，有图标有名字 |
| 界面 | ❌ 有地址栏、有浏览器 UI | ✅ 全屏，无地址栏 |
| 离线 | ❌ 断网就白屏 | ✅ SW 缓存，弱网也能看 |

**第 1 条是决定性的。** 用户端的核心卖点就是「**刷附近店的今日新菜**」——
「附近」全靠定位。响应式网页在手机上打开，定位拿不到，
**整个产品的核心体验就是残缺的**，而这个缺陷在电脑上完全看不出来（因为 `localhost` 是特例）。

> 所以：**响应式解决「能看」，交付形态解决「能用」。**
> 对一个手机产品来说，「能用」才是及格线。
